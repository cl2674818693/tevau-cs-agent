## 1. 背景与目标

### 1.1 现状

- **B 端合作伙伴**通过 `https://tevau.io/ticket/submit.html` 提交问题 → webhook 推送到 Lark 群「Open Api 问题工单通知群」→ 群内 8 名技术值班人员（含钟嘉豪）人工处理 → 表情标记完成。
- **C 端 APP 用户**通过嵌入 APP webview 的 `tawk.to` 与人工客服对话。
- 主要痛点：
  - 工单是非结构化群消息，关键字段（接口名 / 卡 ID / 用户 ID）经常空着，全靠人从「问题描述」自由文本里捞 `uid` / 卡号。
  - 缺数据库化沉淀；SLA 升级靠人脑记。
  - tawk.to 只是聊天工具，无法"读代码 + 查数据 + 自主判断"。

### 1.2 目标（来自录音原话提炼）

不要造工单系统，**要做 AI 引擎**。让 AI 读代码 + 查数据自主判断，而不是配后台。

引擎两大职责：

1. **生命周期管理**（含升级链）—— 由 AI 引擎"启动"工单 + 把外部状态同步回用户对话；真正的状态机由"事项中心"承载。
2. **判断与回应**（含多轮一致性校验）—— AI 在对话里读 3 个代码仓库 + 受限查业务数据库（Nexus 测试库 / APP 后端测试库，详见 §5.5），按问题分类做出判断、给出回复或建单。

### 1.3 一句话定位

> **给客户用的 Claude**：把开发者用 Claude 看代码、查数据库的体验，包装成一个专门答 Tevau Open API/APP 问题的对话框，工具受限、身份隔离、可审计。

## 2. 范围与边界

### 2.1 In Scope（本设计覆盖）

- 一套对话式网页前端（C 端嵌 APP webview / B 端浏览器登录，共用同一套代码）
- AI 引擎后端（Claude 4.x agent loop）
- 工具白名单：代码索引、文档检索、业务库受限查询（多个业务只读库，见 §5.5）、工单出/入 webhook
- 与"事项中心"的 webhook 契约（事项中心未造，本设计定义接口）
- 问题分类、AI 决策路径、多轮一致性校验、Prompt 版本化

### 2.2 Out of Scope（本设计不做）

- **事项中心**自身：分派轮值、SLA 计时、升级到 CTO 的状态机由事项中心实现，本设计只定接口
- **AI 写操作**：MVP 阶段 AI 一律只读 + 诊断 + 转工单。解锁卡片、退款、调额等动作不由 AI 直接执行
- 旧 tawk.to 的数据迁移（保留历史聊天记录的需求另立 spec）
- 旧 `tevau.io/ticket/submit.html` 表单的兼容（B 端切流到对话式网页后停用，旧链路 sunset 计划另立 spec）

### 2.3 关键约束

- AI 工具集**白名单封死**，不暴露自由 SQL / shell / 任意 HTTP
- 所有 `query_*` 工具由后端强制注入会话身份（C 端 user_id / B 端 bu_id），AI 提供的参数会被服务端二次校验是否属于该身份
- 核心 prompt 版本化，禁止把问题分类规则硬编码进代码

### 3.1 组件职责

| 组件 | 职责 | 不做 |
|---|---|---|
| H5 对话前端 | 渲染对话、上传截图、显示工单状态卡片 | 不做业务逻辑、不调 DB |
| AI 引擎后端 | agent loop、工具调度、身份/权限注入、持久化对话与工单；只产出 `category` / `severity` 作为分派输入信号 | 不指定具体分派人、不计算 SLA、不做升级链 |
| 代码索引服务 | 3 个仓库的 grep / read 服务 | 不直连仓库的写权限 |
| DB 受限查询模块 | 一组固定工具，每个工具内置 SQL，参数仅暴露 ID | 不暴露自由 SQL |
| 事项中心（外部） | 分派轮值、SLA 计时、升级链、@CTO | 不做 AI 判断 |

### 3.2 代码仓库（共 3 个）

1. APP 前端（用户在 APP 上看到的界面、流程、按钮）
2. APP 后端（APP 业务逻辑）
3. Open API 后端（对外 API 的实现）

> **代码索引方式**：从 MVP-1 起即用 **Sourcegraph 自部署**（`sourcegraph/server` 单容器版）。引擎的 `search_code` / `read_file` 工具调 Sourcegraph 的 GraphQL API（端点 `/.api/graphql`）。Sourcegraph 后台配 GitLab connector 自动同步 3 个仓库的 `test` 分支，索引由 Sourcegraph 自己管。  
> **优点**：跨仓库统一搜索接口、原生支持 def/ref 跳转、增量索引、有 web UI 给开发者直接看。  
> **代价**：多一个 docker 服务、初次 indexing 需 5-30 分钟（视仓库大小）、需要 admin token 配置。

### 3.3 SSE 协议契约

前后端聊天主链路用 SSE（`text/event-stream`）。本节定义事件类型、心跳、重连、取消生成与错误码，前后端依此对齐。

**端点**：

```
GET /api/v1/chat?conversation_id=<id>
# 鉴权同 §4.1（C 端 JWT / B 端 session cookie）
Accept: text/event-stream
Last-Event-ID: <event_id?>   # 重连时携带，服务端从该事件后补推
```

**事件类型**（`event:` 字段值）：

| event | data | 说明 |
|---|---|---|
| `conversation` | `{ conversation_id, user_type, model }` | 首个事件，携带 user_type（与 §6.2 一致） |
| `message_start` | `{ message_id }` | assistant 消息开始 |
| `content_block_delta` | `{ index, delta: { type: "text_delta", text } }` | 文本流式增量 |
| `tool_use` | `{ tool_use_id, name, input }` | AI 决定调工具 |
| `tool_result` | `{ tool_use_id, output, is_error }` | 工具返回（已脱敏） |
| `message_stop` | `{ stop_reason, usage }` | assistant 消息结束 |
| `ticket_event` | §7.2 入口 webhook 转发的 payload | 工单状态推送（MVP-3 替换轮询，见 §7.5） |
| `mode_change` | `{ from, to, by_staff_id? }` | 会话 mode 切换（§13.2） |
| `human_message` | `{ message_id, sender_staff_id, display_name, content }` | 客服消息（§13.5） |
| `error` | `{ code, message, retry_after_ms? }` | 见下方错误码表 |
| `ping` | `""` | 心跳，每 30s 一次 |

**心跳与超时**：服务端每 30s 发一次 `event: ping`；客户端连续 60s 未收到任何事件视为断线，主动重连。

**重连**：客户端用 `Last-Event-ID` 头携带最后收到的 `id:` 字段。服务端从该事件后补推；服务端事件流必须带稳定 `id:` 字段（消息级别 + 增量级别复合 ID）。

**取消生成**：

```
DELETE /api/v1/chat/{conversation_id}/stream
→ 204 No Content
```

调用后服务端立即中断 Anthropic 调用（abort SDK 请求）、向 SSE 流推一条 `event: message_stop` data `{ stop_reason: "cancelled" }` 后关闭连接。已扣 token 不回滚（Anthropic 不支持），但工具调用计数停止。

**错误码**（`event: error` data.code）：

| code | 含义 | 客户端动作 |
|---|---|---|
| `AUTH_EXPIRED` | JWT/session 过期 | C 端调 `bridge.getToken()` 续 → 重连；B 端跳登录 |
| `RATE_LIMITED` | 单日 token 阈值 100% / 单 IP 限流 | 显示限流提示 + 建工单引导，data 带 `retry_after_ms` |
| `TOOL_DEPTH_EXCEEDED` | 单会话工具调用 > 12 步（§5.2） | AI 自动收尾 + 提示用户新建会话 |
| `MODEL_OVERLOADED` | Anthropic 5xx / 限流 | 客户端退避重试 1-2 次，仍失败则降级提示 |
| `CONVERSATION_NOT_FOUND` | 会话 ID 无效或越权 | 跳转新建会话 |
| `INTERNAL_ERROR` | 服务端未分类错误 | 显示通用错误 + 上报 |

**单 BU/user 单日 token 阈值告警**（§11 line 548）：达到 80% 时推一条 `event: warning` data `{ pct: 80 }`，不中断；100% 时推 `event: error` data `{ code: "RATE_LIMITED" }` 并中断。

## 4. 用户身份与权限

本节定义两端用户如何进入对话框、后端如何识别身份、工具如何受身份约束。

**核心原则：入口决定身份，用户不需要在对话里声明自己是谁。**

两类用户从完全不同的入口进入同一个 AI 引擎后端：

```
普通 APP 用户（C 端）              BU 合作伙伴 / 技术对接（B 端）
       │                                    │
       ▼                                    ▼
 APP 内点"客服"按钮                浏览器访问 chat.tevau.io
（webview 打开 H5 对话页）        （或从 BU 开发者后台跳转）
       │                                    │
 APP 把已登录用户身份透传            先用 BU 账号登录（SSO 或独立账号）
（JWT claims: typ="c", sub=user_id）（JWT claims: typ="b", sub=bu_id）
       │                                    │
       └─────────────┬──────────────────────┘
                     ▼
              同一个 AI 引擎后端
              从 JWT.typ 直接知道是 C 还是 B
                     ↓
        切换不同的 prompt 风格 + 工具权限 + 数据可见域
```

**类比**：淘宝 APP 用户找售后 ≠ 商家在千牛工作台找平台客服。入口本身就是身份，用户不需要在聊天框里声明自己是哪种。

两端典型问法对比（决定 AI 走完全不同的处理路径，详见 §6）：

| 用户 | 典型问法 | AI 处理路径 |
|---|---|---|
| **C 端 APP 用户** | "我的卡为啥被锁了" / "转账失败提示余额不足但我有钱" / "充值按钮点了没反应" | 读 APP 前端代码（理解 UI 流程）→ 读 APP 后端代码（理解业务逻辑）→ 查该用户数据 → 大白话答（详见 §6.2） |
| **B 端 BU 开发者** | "/v2/card/bind 偶发返回 500，uid=1765348436409" / "错误码 DB_TIMEOUT 啥意思" | 查 API 调用日志 → 读 Open API 后端代码 → 技术诊断 + 引用 `file:line` |

下文 §4.1 / §4.2 / §4.3 分别细化身份注入、数据可见域、审计。

### 4.1 身份接入

| 用户类型 | 接入方式 | 身份字段 |
|---|---|---|
| C 端 APP 用户 | APP webview 通过 **JS Bridge** 注入 JWT（不进 URL 不进浏览器历史），后端验签 | `user_id` |
| B 端 BU 合作伙伴 | 浏览器打开网页 → 输入"主账户 ID"（如 `BU00243780`）→ 后端查 DB 校验该 BU 存在且 active → 放行；放行后服务端签发短期会话 cookie | `bu_id` |

**B 端身份方案的已知约束（接受的风险）**：

- 主账户 ID 在合同 / Lark 群 / API 文档示例里多次出现，是"半公开"信息——任何人拿到有效 BU_ID 都能伪装该 BU
- **本方案的安全前提**：本对话系统主要用于"已签约 BU 的开发者技术支持"，受众限定在合作伙伴的技术对接人。如果未来面向更广公众或多租户租用，需要升级为更强的身份方案（API 密钥拼接 / IP 白名单 / 真 SSO）。详见 §11 风险表
- **后端实现要点**：
  - "主账户 ID 校验"调用 `query_bu(bu_id)` 工具的简化版（不带身份过滤，因为这正是身份建立的入口）
  - 校验通过 → 签发 session cookie（`HttpOnly` / `Secure` / `SameSite=Strict`），有效期 8 小时
  - 校验失败 → 返回通用错误"主账户不存在或已禁用"（不区分两种情况，防枚举攻击）
  - 增加频率限制（同 IP 同分钟内最多 5 次尝试，防暴力枚举 BU_ID）

**MVP-1 阶段简化**：B 端用 HTTP header `X-BU-ID` 标识身份（开发联调用，**仅限内网/受信网络**）；MVP-2 起切换为本节定义的"主账户 ID 输入 + 校验"网页流程。

#### 4.1.1 APP JS Bridge 协议

C 端 H5 跑在 **Flutter + flutter_inappwebview** 中。iOS/Android 双端差异由 Flutter 屏蔽——H5 只面对一个统一接口 `window.flutter_inappwebview.callHandler(name, ...args)`。AI 引擎前端 vendor 已有的 bridge 封装（参考 `tevau-finance-h5/src/utils/bridge.ts` 与 `tevau-money-management/src/utils/bridge.ts`，两仓库实现一致）。

**调用约定**：

```ts
// 统一返回结构
interface BridgeResponse<T> { code: number; data: T; message: string }
// code === 0 表示成功

// 调用入口
window.flutter_inappwebview.callHandler(name, ...args): Promise<BridgeResponse>
```

**Ready 协议**：冷启动时 H5 `onMounted` 可能早于 bridge 注入。调用任何 handler 前必须 `await bridge.whenReady()`——内部轮询 `window.flutter_inappwebview` 是否存在，poll 50ms / timeout 5s。`whenReady` 返回 `false` 时降级到 URL query 兜底（开发环境 / 旧 APP 升级页）。

**本系统用到的 handler**（均已在参考仓库实现）：

| handler | 用途 | 时机 |
|---|---|---|
| `getEnv` | 拿 `EnvInfo`（包含 `language` / `platform` / `version` / `env`） | 首屏初始化（驱动 §6.2 语言镜像、限流提示语等） |
| `getToken` | 拿用户 JWT（不进 URL/历史） | 首屏 + 401 续 token |
| `navigate` | 跳转 APP 原生页面（如引导用户去"修改密码"页） | AI 在回复里给出原生跳转建议时 |
| `close` | 关闭 webview | 用户点退出 |
| `uploadImage` | 调起原生相册/相机选图（用户上传截图作证据） | 在对话框工具栏触发 |
| `setLocale` | 通知 native 切换语言 | 用户在对话内主动切语言时（次要） |

**Token 刷新**：SSE 收到 `event: error` data `{ code: "AUTH_EXPIRED" }` 时，调 `bridge.getToken()` 拿新 token，重连 SSE。getToken 失败 → 走 `bridge.logout()` 退到 APP 登录页。

**Bridge 不可用 fallback**（旧 APP / 浏览器调试）：从 URL query 读 `token / lange / env` 兜底；只允许在开发环境或显式"旧 APP 升级提示页"场景使用，生产 webview 必须走 bridge。

### 4.2 数据可见域（强制）

所有 `query_*` 工具在被 agent 调用时：

1. 服务端**强制**用当前会话身份覆盖（或注入）查询参数
2. 即便 AI 在参数里写了其他 ID，服务端二次校验：该 ID 是否属于当前身份。不属于 → 拒绝调用并把拒绝事实回灌给 agent，让它修正
3. 跨身份查询能力（如 BU 想看自己 BU 下任意 user 的数据）由各工具的 SQL 显式声明 join 条件，不由 AI 自行决定

### 4.3 审计

每次工具调用记录：`session_id / user_or_bu_id / tool_name / params(脱敏前后) / result_size / cost_ms / 是否被拒`。审计日志保留 ≥ 180 天。

**存储方案：阿里云 SLS（Simple Log Service）**：

- 写入：AI 引擎通过 SLS Producer SDK 异步批量写（非关键路径，失败本地落盘 + 重试）
- Project：`tevau-ai-engine-audit`；Logstore：`tool-calls`（工具审计）/ `chat-events`（对话事件）/ `staff-actions`（客服操作）
- 保留期：SLS 配 **180 天** 热数据 + **OSS 归档**（更长留存按合规要求另配）
- 不可篡改：SLS 默认 **append-only**（无更新/删除 API）；每日定时跑 hash 校验作业，对比 SLS 数据与本地 hash chain，发现不一致告警
- 备选（不推荐）：PG 表 + 定期 dump 到 OSS——只有 SLS 不可用时启用，需要自行实现归档与不可篡改保证

### 4.4 审计查询接口

```http
GET /admin/audit?session_id=&staff_id=&user_or_bu_id=&tool_name=&time_range=&limit=
Authorization: <staff_jwt>     # 仅 senior / engineer + 合规组角色可查
→ 200 { items: [...], next_cursor: "..." }
```

**ACL**：
- `agent` role 不可访问
- `senior` 可查自己接管过的会话审计
- `engineer` 可查全部
- **合规组**额外用 `compliance` 子 role（在 staff.role 之外加一个 flag），可查全部 + 可导出
- 查询本身写一条 **meta-audit**（"`<staff_id>` 在 `<time>` 查了 `<filter>`，返回 `<rows>` 条"），存到同一 SLS Logstore `staff-actions`

> 注：本节定义的是**用户身份**（C 端 APP 用户 / B 端 BU 合作伙伴）。**客服身份（staff）** 走独立认证体系，详见 §13.3。

## 5. AI 工具集（白名单）

### 5.1 工具清单（初版，需后端对接细化）

> **本节工具签名和具体 SQL 是占位 / 范例**，上线前必须与 APP 后端 / Open API 后端开发同学对齐字段、表、性能、敏感字段脱敏规则。本 spec 只确立**白名单工具的形态**，不冻结清单。

| 类别 | 工具 | 参数 | 说明 |
|---|---|---|---|
| 代码 | `search_code(repo, query, max_hits=50)` | repo ∈ {`app_frontend`,`app_backend`,`openapi_backend`} | grep 风格 |
| 代码 | `read_file(repo, path, start_line?, end_line?)` |  | 整文件或片段 |
| 文档 | `lookup_api_doc(query)` | | 检索 api-docs.tevau.io 索引 |
| 数据 | `query_user(user_id)` | | 用户基本信息（脱敏） |
| 数据 | `query_card(card_id)` | | 卡片状态、是否锁定、锁定原因/规则命中 |
| 数据 | `query_api_call(uid_or_trace_id)` | | API 调用日志（请求、响应、耗时、报错） |
| 数据 | `query_bu(bu_id)` | | B 端可见；BU 基础信息 |
| 数据 | `query_user_orders(user_id, limit=20)` | | 订单 |
| 数据 | `query_risk_events(user_id_or_card_id, limit=20)` | | 风控事件 |
| 工单 | `create_ticket(category, summary, evidence, severity)` | | 出口：触发 webhook 推事项中心。**AI 引擎不指定分派人**，分派由事项中心按配置规则决定（见 §7.3） |
| 工单 | `query_ticket_status(external_ticket_id)` | | 反查事项中心当前状态 |

### 5.2 工具调用的强制约束（引擎实现）

- 单次会话工具调用深度上限：12 步（防 agent 抽风死循环）
- 单工具单次结果体上限：256 KB（超出强制裁剪 + 提示 agent 缩范围再查）
- `query_*` 类工具的 SQL **内置在工具实现里**，参数化绑定，绝不拼接 AI 输入的字符串
- `search_code` 对 `query` 做长度与模式校验，禁止 regex 灾难性回溯模式

### 5.3 待对接事项

- 完整工具清单（哪些查询是高频的？哪些字段必须脱敏？）
- DB 只读副本/账号（建议走只读副本，避免影响生产）
- 各工具的 SLA（单次调用 P95 < 500ms 是个合理目标，事关用户对话延迟体感）

### 5.4 数据脱敏规则（强制在工具层做，不靠 LLM 自觉）

**脱敏在 `query_*` 工具层完成**：从 DB 取出原始字段后，**工具 handler 内**统一脱敏后再返回给 agent，不让原始敏感值进入 LLM 上下文。LLM 永远看不到原文，也就无从泄露。

| 字段类型 | 脱敏规则 | 示例 |
|---|---|---|
| 手机号 | 保留前 3 + 后 2 | `138****12` |
| 身份证 / 护照 | 保留前 2 + 后 2 | `33****12` |
| 银行卡号 | 保留前 4 + 后 4 | `4938 **** **** 4590` |
| 邮箱 | 本地部分保留 2 字符 + `***` | `ab***@x.com` |
| 内部风控规则名/编号（如 `R-217`） | **完全去除**，替换为业务原因翻译（如"风控误判，触发卡片锁定规则"） | — |
| 内部 SQL 表名 / 列名 | 不出现在工具返回的 JSON key 里（用业务语义命名） | — |

具体字段清单与脱敏规则需后端 + 风控对齐后冻结，**冻结后写入 `prompts/security.md` 与各工具实现**。

### 5.5 引擎自身库 vs 业务只读库（必须分离）

引擎涉及两类持久化，**绝不混用**：

| 库 | 用途 | DB 类型 |
|---|---|---|
| 引擎自身库 | 对话历史、工具调用审计、本地工单副本、prompt 版本记录 | SQLite（MVP-1）/ PostgreSQL（生产） |
| 业务只读库（多个） | `query_*` 工具读的真实业务数据，**单 RDS 实例 + 多业务库**：`unlimitpay_test`（Tevau 主，必接，走 `tevau_test_read` 只读账号）+ `nexus_test`（Nexus 项目，次接，需 DBA 配只读账号）；`wot_*` / `t_tevau_api_saas` 待确认是否接 | MySQL 8.0（阿里云 RDS） |

**实现要求**：
- 引擎自身库使用一套连接（`aiosqlite` / `asyncpg`）
- 每个业务只读库各自独立连接池（`aiomysql`），只读账号、最小权限
- 工具实现里禁止跨库 join、禁止从引擎库回写业务库
- 配置项 `.env` 里**每个业务库一个连接 URL**（如 `NEXUS_DB_URL` / `TEVAU_DB_URL`），不要复用 `DB_URL`

> MVP-1 阶段可以用一套 SQLite mock 业务数据（见 plan Task 6 的 `mock_*` 表），但 MVP-2 接真实库时这部分 query_* 工具必须重构为 aiomysql 实现。这是 plan 的**已知重构点**，不是隐藏债务。

#### 5.5.1 mock → 真库迁移协议

MVP-1 工具基于 SQLite mock；MVP-2 切真 MySQL。为把迁移成本控制在 handler 内，明确以下约定：

1. **工具签名跨阶段稳定**：`query_*` 工具的参数列表 + 返回 JSON schema **不变**。MVP-1 mock handler 与 MVP-2 真库 handler 对前端 / AI / prompt 完全等价
2. **Mock 字段集 freeze 时点**：MVP-1 启动前 1 周通过 PR 锁定 mock 表的字段集（写进 `prompts/security.md` 与各工具 docstring），freeze 后只允许加字段不允许改/删
3. **真库 schema dump 时点**：MVP-2 启动前 1 周由后端提供 `unlimitpay_test` + `nexus_test` 真表 dump（§12.2 第 9 条）；引擎方做 mock ↔ 真库字段 diff，发现不一致项立即提工单对齐
4. **脱敏字段对齐**：mock 中已脱敏的字段在真库 handler 里**继续脱敏**（脱敏规则按 §5.4），不因换库而漏
5. **Prompt few-shot 抽象层**：`prompts/examples/*.md` 里的工具调用示例**只用工具签名层抽象**（参数名 / 返回字段名），不出现具体真库表名 / 列名；保证换库时 prompt 无需改动
6. **回归用例**：MVP-1 末期产出一组 query_* 工具的 contract test（输入参数 → 期望返回 schema），切真库后用同一组 test 验证 handler 等价性

## 6. 问题分类与 AI 决策路径

### 6.1 问题分类（录音原话 4 类 + 人工介入）

| 类型 | 触发条件 | AI 行为 | 是否建单 |
|---|---|---|---|
| 无信息 | 缺关键字段（uid / 卡 ID / 接口名等） | 追问，引导用户补齐 | 否 |
| CQ（咨询） | 文档/代码里能找到答案 | 当场答，引用代码位置 / 文档段落 | 否 |
| 事务 | 需查数据才能定位 | 查数据 → 给诊断结论；若需"动手改"（解锁/退款/调额） | **是**（转人工执行） |
| bug | 疑似系统缺陷 | 收集证据（日志、相关代码位置、复现步骤） | **是**（category=bug） |
| 商务/账户操作 | C 端非技术性问题（注销账号 / 退款 / 绑卡换绑 / 调额 / 发票 / 修改绑定手机等） | **不查代码、不查 DB**（除身份确认外）；给标准引导话术（APP 自助页 / 转人工）；默认建 `category="人工介入"` 转 agent | **是**（category=人工介入） |
| 人工介入 | 用户点"转人工"按钮 / AI 判定 AI 不适合答（如情绪化、合规边界、AI 反复答不对） | 立即停止 AI 决策路径 → 调 `create_ticket(category="人工介入")` → 走 §13 客服介入流程 | **是**（category=人工介入） |

> **商务/账户操作类的标准引导清单**仍待产品方确认（见 §12.1 [TBD]）——具体哪些场景走自助页、哪些必须转人工、引导话术文案，MVP-2 启动前由产品出。MVP-1 期间该类问题统一走"人工介入"兜底。

### 6.2 C 端"APP 行为咨询"场景（关键补充）

C 端 APP 用户的问题往往是从**自身操作体验**出发：

- 例 1：「我点充值按钮没反应」
- 例 2：「我的卡为啥被锁了？」
- 例 3：「转账失败提示余额不足，但我明明有钱」
- 例 4：「这个功能在 APP 哪里？」

这类问题在分类上仍落进 **CQ** 或 **事务**，但 AI 的处理路径有 C 端特有的"三层下钻"：

```
1. 读 APP 前端代码：理解用户描述的界面/按钮/流程在代码里的位置，确认 UI 行为
                 ↓
2. 读 APP 后端代码：理解该操作触发的业务逻辑、可能的失败路径与错误码
                 ↓
3. 查该用户数据：用 query_user / query_card / query_api_call 等定位用户该次操作的实际记录
                 ↓
4. 综合给出 C 端用户能听懂的语言化解释（不要把代码贴给用户看）
```

**输出语言原则**：
- C 端用户：自然语言、不显露代码、不显露内部表名，最多说"系统记录到您 X 时间做了 Y 操作，结果是 Z"
- B 端 BU 合作伙伴：可显露技术细节（接口路径、错误码、代码引用），他们是开发者
- **两端共同红线**：内部风控规则名/编号（如 `R-217`）、敏感字段明文（手机号/身份证/全卡号）一律脱敏；C 端连规则名都不露，只翻译为业务原因

**user_type 在 SSE 协议中的传递**：前端无法从 URL 判断当前是 C 端还是 B 端（同一套 React 代码在 APP webview 和浏览器里都跑）。后端在 `/api/v1/chat` 的首个 SSE 事件（`event: conversation`）的 data 里携带 `user_type` 字段，前端据此切换提示语、是否显示工程师视角的 ToolCallChip 详情、TicketCard 的字段密度等。

**会话初始化端点（首屏渲染依赖）**：前端在打开对话框、发首条消息**之前**先调一次 REST 端点拿到首屏渲染依赖与会话 ID，避免 SSE 首事件到达前前端无渲染依据 / 错误态无处显式呈现：

```http
POST /api/v1/conversations
# 鉴权同 §4.1（C 端 APP bridge 注入的 JWT / B 端 session cookie）
Content-Type: application/json
{ "resume": "<conversation_id?>" }      // 可选：传入则恢复历史会话，否则新建

→ 200
{
  "conversation_id": "conv_abc123",
  "user_type": "c" | "b",
  "display_name": "李 ** 华",            // 当前用户显示名（已脱敏，C 端用昵称、B 端用 BU 名）
  "greeting": "您好，我是 Tevau 智能助手…", // 后端按 user_type 选好的首屏招呼语
  "history_url": "/api/v1/conversations/conv_abc123/messages?limit=20",  // 可选：恢复历史时由前端再调
  "limits": { "daily_token_used_pct": 12, "max_turns": 20 }              // 可选：用于前端提前提示用量
}

→ 401 / 403 / 429 等错误状态在此层显式返回，前端据此渲染登录失效 / 限流提示
```

随后前端再开 SSE `GET /api/v1/chat?conversation_id=conv_abc123` 拉流。**此端点的设计目的**：把首屏依赖（user_type / display_name / greeting / limits）与错误状态从 SSE 长连解耦到 REST 短请求，前端可以在等待 SSE 首事件期间用同步拿到的 user_type 渲染骨架屏与 ToolCallChip 占位区。

**AI 回复语言策略：镜像用户输入语言**：AI 引擎不依赖 JWT.locale 或前端透传的语言字段，而是**由 system prompt 强制要求 AI 镜像用户最近一条 user message 的语言**——用户用中文问就用中文答，用英文问就用英文答，混用就跟随主体语言。落地要点：
- `prompts/system/reply_style.c.md` / `reply_style.b.md` 顶部固定一句话约束："Always reply in the same language as the user's latest message. If unclear, default to the language of the conversation so far."
- system 消息（如"已为您接通客服 张三"、"工单已关闭"）由 AI 引擎按 **当前会话主体语言** 渲染（每个会话维护一个 `inferred_locale` 字段，AI 每次回复后更新）；不依赖前端语言设置
- few-shot examples（§9）准备中/英两版，根据 `inferred_locale` 注入
- 工具返回值的"业务语义命名"字段（§5.4）保留英文 key，但工具内置的固定文案（如错误描述）跟随 `inferred_locale` 渲染

### 6.3 严重度（severity）的判定

`create_ticket` 调用时由 AI 推断并写入：

| severity | 典型场景 |
|---|---|
| p0 | 资金类异常、可能涉及多用户、合规风险 |
| p1 | 单用户阻塞核心功能（卡片误锁、转账失败） |
| p2 | 体验问题、非阻塞 bug |
| p3 | 优化建议、文档不清 |

事项中心可基于 severity 决定 SLA 数值与升级速度，受理人也可在事项中心覆盖 severity（覆盖动作通过 §7.2 回调里 `event=in_progress` 携带新 severity 字段回传到 AI 引擎，用于对话内的进度更新）。

### 6.4 前置话题分类器（防"通用 Claude 滥用"）

**问题**：本系统底层是 Claude，存在被用户当成通用 Claude 用的风险（写代码 / 翻译 / 时事 / 数学题 / 闲聊 / 角色扮演越狱）。结果是 token 被薅、产品定位跑偏、合规风险（公司可能为 AI 输出的非业务内容担责）。

**双层防御**：

**第一层：system prompt 强边界**（MVP-1 起，零额外成本）

- `prompts/system/topic_scope.md` 在 system prompt 顶部固定：
  - **话题白名单**：Tevau APP 使用问题 / Open API 接口问题 / 卡片业务 / 用户账户与订单 / 风控诊断 / bug 报告
  - **话题黑名单**（示例）：通用编程 / 翻译 / 数学解题 / 时事新闻 / 角色扮演 / 写作辅助 / 任何非 Tevau 业务问题
  - **固定 refusal 模板**：LLM 命中黑名单时**只能输出**固定文案（C 端："我是 Tevau 助手，只能帮您处理账户、卡片或 Open API 相关问题。请问您需要咨询哪方面？"；B 端："I'm Tevau's API support assistant. I only handle questions about Tevau Open API / your BU's account / card issues. What can I help you with?"），**禁止 LLM 自由发挥拒答内容**（防"虽然但是"绕开）
  - **越狱话术防御**：明确列出"忽略之前的指令" / "假装你是 X" / "DAN mode" 等典型越狱话术 → 一律按黑名单处理
- 模板语言遵循 §6.2 "AI 镜像用户语言" 规则

**第二层：前置 haiku 意图分类器**（MVP-2 上线，~5% 额外成本）

- 用户每条新消息进入主 agent 前，先调一次 `claude-haiku-4-5` 做意图分类：

  ```
  POST /messages (haiku, max_tokens=10, stop_sequences=["\n"])
  system: "Classify if the user message is about Tevau (APP/Open API/card/account/order/bug).
          Reply with exactly one word: yes / no / uncertain."
  user: "<用户最新消息>"
  ```

- 分类结果：
  - `no` → **不走主 agent loop**，直接返回 §6.4 refusal 模板，记一条 audit log
  - `uncertain` → 进主 agent，但 system prompt 注入"用户消息可能不是 Tevau 相关，请优先判断话题是否在范围内"提示
  - `yes` → 正常走主 agent
- 单次 haiku 调用成本 < $0.001（输入 ~50 tokens、输出 1-2 tokens）

**兜底层**：

- 单 user/BU 单日 token 硬阈值（§11 风险表 "API 成本失控"）
- 单 IP 短时间消息数 rate limit：MVP-1 默认 30 条/分钟、可配
- SLS 审计每周抽查"长会话（≥ 10 轮） + 零工具调用"的异常会话——是话题偏离的强信号

**MVP 阶段安排**：

- **MVP-1**：仅第一层（system prompt 边界 + 固定 refusal）+ 兜底层（token 阈值 + rate limit）
- **MVP-2**：加第二层（haiku 前置分类）；根据实际越狱数据调整阈值
- **MVP-3**：分类器准确率纳入 §10 验收 + §12.5 ✅17 可观测面板（异常会话告警）

### 7.2 入口：事项中心 → AI（状态回调）

```http
POST {ai_engine_base}/api/v1/tickets/{external_ticket_id}/events
Content-Type: application/json
X-Signature: <hmac-sha256(body, shared_secret)>

{
  "event": "assigned" | "in_progress" | "escalated" | "resolved" | "closed" | "reopen",
  "actor": "<assignee_name>" | "CTO" | "user" | "system",   // 处理人姓名由事项中心传入，AI 引擎不预先知道
  "comment": "已处理，卡片已解锁。原因：风控误判 R-217。",
  "internal_ticket_id": "EC-2026-05-18-00042",
  "severity": "p0" | "p1" | "p2" | "p3",                    // 可选：仅 event=in_progress 且受理人在事项中心覆盖了 severity 时填；AI 引擎据此更新本地工单镜像和对话内进度提示（见 §6.3）
  "reason": "用户表示问题未解决：重新被锁了",   // 仅 event=reopen 时填，来自 §7.6 user_rejected_resolved
  "at": "2026-05-18T15:42:11+08:00"
}
```

AI 引擎收到回调后：
- 持久化事件 → 在该会话的对话流里追加一条系统消息（"您的工单已被嘉豪受理 / 处理完成，结论：……"）
- `resolved` 后给用户一个评价入口（可选 MVP-3）

### 7.3 SLA 与升级链（由事项中心实现，AI 不计时）

事项中心**配置**而非引擎硬编码：

| 阶段 | 默认值（建议） | 动作 |
|---|---|---|
| 第一接收人 | 当前值班（事项中心按配置的值班表 + 分派规则决定） | 创建即分派 |
| SLA1 超时 | 按 severity：p0=1h / p1=5h / p2=24h / p3=72h | 升级到下一接收人（同 role 内轮换） |
| SLA2 超时 | 默认 SLA1 × 2（事项中心可配） | 升级 @CTO |
| reopen | 用户拒绝 resolved（§7.6 `user_rejected_resolved`） | 工单状态回到 `assigned`，重新分派，**SLA1/SLA2 计时重新开始** |

> **AI 引擎不感知值班表与对接人姓名**。所有分派规则（如 "category=bug → 嘉豪"、"SLA1=5h"、值班轮转、CTO 升级条件）由事项中心配置与维护；AI 引擎只产出 `category / severity / evidence` 作为输入。AI 引擎对话里显示的处理人姓名来自事项中心 §7.2 回调里的 `actor` 字段，不由引擎本地维护。

### 7.4 鉴权与密钥轮换

双向 webhook 使用 HMAC-SHA256 共享密钥签名（`X-Signature` 头）。

**轮换机制（不能停服）**：
- 同时支持 **两把 active key**（`current` + `previous`）。验签时任一通过即可
- 密钥配置项：`EVENT_CENTER_SECRET_CURRENT` + `EVENT_CENTER_SECRET_PREVIOUS`
- 轮换流程：(1) 生成新密钥写到 `current`，老 current 滚到 `previous`，触发热加载；(2) 通知事项中心同步更新；(3) 灰度期（≥ 1 天）观察双 key 验签成功率；(4) 灰度通过后把 `previous` 清空
- 周期：每季度强制 + 任何泄漏迹象立即触发

### 7.5 工单状态实时推送到用户对话（实现机制）

事项中心回调到达 `/api/v1/tickets/{id}/events` 后，AI 引擎不能只持久化，还得让用户在对话里立刻看到。两种实现路径：

| 方案 | 描述 | 选用阶段 |
|---|---|---|
| **A. 轮询** | 前端每 10s 拉一次 `/api/v1/conversations/{id}/updates`，返回该会话所有未读工单事件 | MVP-1 默认 |
| **B. SSE 长连** | 前端打开一个 `GET /api/v1/conversations/{id}/stream` SSE，后端收到回调后立刻推送 | MVP-3 升级 |

MVP-1 用方案 A 即可，避免 SSE 长连的连接管理复杂度；上线后如延迟体感差再升级到 B。

### 7.6 用户确认与重新打开

`resolved` 之后工单不会自动关闭——必须由用户确认或超时兜底。三种方式组合：

| 方式 | 触发 | 谁实现 | 必要性 |
|---|---|---|---|
| **显式按钮**（已解决 / 未解决） | 用户点 TicketCard 上的按钮 | AI 引擎前端 + 引擎 API | 必做 |
| **超时自动 closed** | resolved 后 X 天（默认 3 天）用户未操作 | 事项中心定时扫描 | 必做（防工单永远挂起） |
| **评价对话框** | closed 后弹 1-5 星评价 | 引擎前端 | 可选（MVP-3） |

**对话里的渲染**：

```
┌────────────────────────────────────────┐
│ 您的工单 AI-2026-05-18-7a3f1c 已处理完毕 │
│ 处理人：嘉豪                              │
│ 结论：卡片已解锁，原因是风控误判           │
│                                          │
│   [ ✓ 已解决 ]    [ ✗ 未解决，重开 ]      │
│   （3 天未操作自动关闭）                  │
└────────────────────────────────────────┘
```

**反向 webhook 协议（前端 → AI 引擎，区别于 §7.1-7.2 与事项中心的 webhook）**：

```http
POST {ai_engine}/api/v1/tickets/{external_id}/user-events
Content-Type: application/json
# 鉴权：从当前会话身份解析（C 端 JWT / B 端 session cookie），由同一个身份解析中间件验签；不硬性要求 Bearer header

{
  "event": "user_confirmed_resolved" | "user_rejected_resolved",
  "reason": "重新被锁了",            // 仅 user_rejected_resolved 时填
  "at": "2026-05-18T16:00:00+08:00"
}
```

> 注意：本端点用**会话身份验签**（不是 HMAC）——来源是浏览器/APP 而非另一台服务。引擎从当前 session 解析身份（C 端 APP bridge 注入的 JWT → user_id；B 端 session cookie → bu_id），再二次校验该 `external_ticket_id` 是否属于该身份，不属于则 403。与 §4.1 身份方案保持一致，避免前端为该端点单独处理 Bearer。

**引擎收到后的处理**：

- `user_confirmed_resolved` → (a) 本地标 closed；(b) 经由原 webhook（§7.1）通知事项中心 `closed`；(c) 对话追加系统消息"工单已关闭，感谢您的反馈"；(d) 可选触发评价对话框（MVP-3）
- `user_rejected_resolved` → (a) 本地标 reopen；(b) 经由原 webhook 通知事项中心 `reopen`（携带 user reason）；(c) 事项中心重新分派 → 工单回到 `assigned` 重启升级链；(d) 对话追加"已通知工程师重新跟进"

**边界情况**：

- **用户关页面跑了 / 没点按钮**：靠"超时自动 closed"兜底（事项中心实现定时扫描），不会永久挂起
- **用户对 closed 仍有异议**：引导其在对话里继续问 → 触发"24h 内已有相关工单 → 追加证据到该单"逻辑（§11 工单风暴对策），实质上是 reopen 的另一条入口
- **C 端 vs B 端按钮文案**：C 端用"已解决 / 没解决"自然语言；B 端可多一个"附加日志/截图"按钮丰富证据（详见 §6.2 输出语言原则）

**MVP 阶段安排**：

- MVP-1：显式按钮 + 超时兜底已实现（前端按钮 + 反向 webhook 端点 + 引擎转发到事项中心）；超时定时扫描在事项中心 mock 阶段先简化为"resolved 后 3 天直接 closed，不发回调"
- MVP-3：评价对话框 + 评价数据进可观测面板

## 8. 多轮一致性校验

### 8.1 会话内一致性

每次 agent 准备给出"诊断结论"前，system prompt 强制 self-check：

> 在本次回复前，回看本对话中你之前给过的诊断/结论。若本次结论与之前不同，**必须显式标注修订点**（"之前我判断是 X，基于新查到的 Y，现更新为 Z"），不能默默改口。

### 8.2 跨工具事实优先级

当不同信源结论矛盾时，AI 必须按以下优先级取舍并显式说明：

```
数据库 > 代码 > 文档       （结构性事实）
线上日志 > 代码注释        （运行时事实）
```

例：API 文档说"卡片绑定接口同步返回结果"，但代码里看到是异步 + 回调；以代码为准。代码注释说"该函数 5 秒超时"，但线上日志 P99 是 8 秒；以日志为准。

### 8.3 实现要点（强制由代码 inject，不能靠 LLM 自觉）

LLM 看到 `self_check.md` 不等于会执行 self-check。必须由 **agent runtime 代码强制** inject 一个独立步骤：

1. agent 在 `stop_reason == "end_turn"`（即模型认为可以收尾）后，**先不流出最终文本**
2. 由 runtime 追加一条 user 消息：`"在你给出上面这段最终回复之前，请按 self_check 规则做一次审视：…（注入 self_check.md 全文）"`
3. 再调一次 `messages.create`，让模型基于上文 + self_check 规则给出修订后的回复
4. 把这一次结果作为真正的最终输出流给前端
5. self-check 本身计入 `cost_guard` 的 token 但**不计入**工具调用深度（避免占额）

代价是单次对话多一轮 LLM 调用。可通过 prompt cache 把 self_check.md 缓存掉降低成本。**这一步在 MVP-3 上线**（MVP-1/2 阶段仅靠 system prompt 里的 self-check 段落，效果弱但不破坏功能）。

矛盾发现时不静默忽略——把矛盾写进回复或工单 `evidence`，让人能追溯。

## 9. Prompt 即配置（"通过写 prompt 管理"）

### 9.1 Prompt 资源化

核心 prompt 文件放在 git 仓库的 `prompts/` 下，结构：

```
prompts/

    role.md                  # AI 角色定义

    reply_style.b.md         # B 端技术化回复风格
    self_check.md            # 多轮一致性 self-check 模板
    security.md              # 数据脱敏字段清单与规则（§5.4）
  examples/
    cq_card_lock.md          # 几条 few-shot 示例
    bug_api_500.md
    transaction_unlock.md
```

### 9.2 版本与灰度

- 每个 prompt 文件带 frontmatter `version: 1.3.0`
- 部署时把 prompt 编译进引擎（或运行时从配置中心拉）
- 支持灰度：按 `bu_id` / `user_id` 哈希分桶选 prompt 版本
- 改 prompt 走 PR review，禁止直改线上

### 9.3 模型版本锁定

- prompt 文件里显式声明 `model: claude-sonnet-4-6` 或 `claude-opus-4-7`
- MVP 默认 `claude-sonnet-4-6`（成本敏感），复杂诊断路由到 `claude-opus-4-7`（在 system prompt 里加路由 hint，或由前置分类器决定）

### 9.4 AI 答错数据回流 [TBD 占位]

**问题**：MVP-1/2 阶段 AI 答错时，客服只能口头反馈，没有结构化沉淀路径。这是 AI 产品迭代效率的命门，但具体机制需要产品决策（见 §12.1）。

**推荐方向**（待产品确认）：
- 客服在工作台 `release` 或 `human_takeover` 后，如果改写了 AI 的最后一条回复，自动落"修正样本"表（`prompt_correction_samples`：会话 ID / 原 AI 回复 / 客服改写 / 客服 staff_id / 时间 / 是否进 examples）
- 每周由 prompt 维护人（默认嘉豪 + AI 工程对接人）review 修正样本，标记 "进 examples / 弃用 / 调 prompt 规则" 三态
- 标记为"进 examples" → 自动开 PR 到 `prompts/examples/`，走 §9.2 PR review

**MVP 阶段**：
- MVP-1/2：仅落表，不强制 review（客服小规模、AI 流量低）
- MVP-3：强制每周 review + 落地到 prompt 更新

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| API 成本失控 | 强制 Anthropic prompt cache；单会话工具调用深度 ≤ 12；**单日单 BU / 单 user 的 token 硬阈值**（达到 80% 提醒、100% 拒服并提示工单）；模型分级路由（默认 sonnet-4-6，命中复杂诊断规则路由到 opus-4-7） |
| 成本估算（已知粗算） | 单次对话：sonnet-4-6 约 $0.05-0.15；opus-4-7 约 $0.30-0.80。50 次/天 BU 用量一个月 $100-1200。**预算盘子待定（§12 未决项）**，决定默认模型与升 opus 的阈值 |
| 会话长度不受控 | 单会话上限：(a) ≤ 20 轮对话；(b) ≤ 100K input token。超出 → 自动触发"总结+开新会话"流程，把前次诊断浓缩为一段 context 注入新会话 |
| AI 答错误导用户 | 每条 AI 回复底部固定"没解决？转人工 →"按钮，一键建单兜底；C 端 MVP 上线初期保留 tawk.to 作为应急人工入口（灰度切流，非一次性切换） |
| 数据越权 | 工具调用层强制注入身份 + 服务端二次校验 + 全量审计；DB 只读副本独立账号最小权限 |
| 用户身份伪造 | MVP-1 临时 `X-BU-ID` header 方案 **仅限内网/受信网络**；MVP-2 起 B 端用"主账户 ID 输入 + DB 校验"简化方案，**接受其伪造风险**（BU_ID 视为半公开、对话系统受众限定于已签约 BU 的技术对接人，详见 §4.1）；C 端走 APP JS Bridge 注入 JWT，相对安全；未来若扩到更广受众需升级 B 端身份方案 |
| engineer 数据访问审计 | `engineer` role 可看原始敏感字段（手机/身份证/规则名 R-217 全部不脱敏，见 §12.5 ✅9）；强制全量审计 + 内部合规组定期 review 操作日志；可疑访问模式（如短时间扫多用户）触发告警 |
| 敏感字段泄漏 | 脱敏在工具层做（§5.4），原文不进 LLM 上下文；LLM 输出再做正则兜底扫描（手机号/身份证/全卡号格式），命中即 redact |
| 模型漂移 | prompt 文件锁定模型 ID；prompt + 模型一起版本化；切模型走灰度 |
| Prompt 注入攻击 | 系统消息与用户消息严格分离；工具结果带 `<tool_result>` 包装；用户消息里出现的"指令性 prompt"被 agent 显式忽略（在 system prompt 里写规则） |
| 工单风暴（用户被引导建过多单） | AI 建单前检查同会话/同用户 24h 内开放工单数，超阈值改为追加证据到已有单 |
| **用户把系统当通用 Claude 用**（写代码 / 翻译 / 时事 / 数学题 / 闲聊 / 角色扮演越狱） | 双层防御：(a) **system prompt 强边界**——`prompts/system/topic_scope.md` 顶部固定话题白名单（Tevau APP / Open API / 卡片业务 / 用户账户）+ 固定 refusal 文案模板（"我是 Tevau 助手，只能帮您处理账户/卡片/Open API 问题…"），LLM 不允许自由发挥拒答内容；(b) **前置 haiku 意图分类器**（MVP-2 上线，见 §6.4）：每条用户消息先调 `claude-haiku-4-5` 做 `is_tevau_topic?` 三态分类，`no` → 直接返回 refusal 模板**不走主 agent loop**（省 sonnet token）。兜底：单 user/BU 单日 token 阈值（本表"API 成本失控"行）+ SLS 审计每周抽查"长会话 + 零工具调用"异常会话（强滥用信号） |

## 13. 人工客服介入

AI 引擎不是纯 AI——客服人员需要能介入到对话里。**目标形态：C 方案（含 AI 辅助 + 草稿模式）**，但分三阶段递进实施。

### 13.1 三种介入模式（递进）

| 模式 | 关键行为 | 典型场景 | 阶段 |
|---|---|---|---|
| **A. 异步介入** | 用户点"转人工" → AI 建 category=人工介入工单 → 推事项中心 / Lark @ 值班客服 → 客服走 Lark / 电话 / 邮件回复 | MVP-1 兜底，开发量为零 | MVP-1 |
| **B. 网页内接管** | 客服在工作台点"接管"该会话 → 状态变 `human_takeover` → 后续用户消息**跳过 AI**，直接转给客服 → 客服回复经 SSE 推回对话框（消息气泡显示 `[客服 张三]`） → 客服可"释放回 AI" | 用户体验完整、不切通道 | MVP-2 |
| **C. AI 辅助 + 草稿 + 多客服协作** | 在 B 基础上：客服旁观模式（不接管但可看到 AI 在调什么工具）；草稿模式（高风险问题 AI 出回复 → 客服 review 后才发）；客服调 AI 工具（让 AI 在工作台代查数据但不发给用户）；多客服并发管理（抢单 / 转工程师 / KPI） | C 端规模化或高合规要求时启用 | MVP-3 |

### 13.2 会话模式状态机

会话表（`conversations`）新增字段 `mode`：

```
        用户开新会话
              │
              ▼
        ╔════════╗
        ║   ai   ║  ← AI 主导（默认）
        ╚════╤═══╝
             │
   ┌─────────┴────────────┐
   │                      │
   │ 用户点"转人工"        │ 系统规则触发（如 severity=p0 / 高风险）
   │ 或 AI 判定需人工      │
   ▼                      ▼
╔══════════════╗     ╔═══════════╗
║human_pending ║────►║ ai_draft  ║   ← AI 出回复但不发用户，待客服审
╚══════╤═══════╝     ╚═════╤═════╝
       │ 客服接管               │ 客服 approve → 发出
       ▼                       │ 客服 reject  → 客服重写
╔═══════════════╗               │
║human_takeover║◄──────────────┘
╚══════╤═══════╝
       │ 客服点"释放"
       ▼
   回到 ai

任何状态都可被客服切到 human_takeover（强制接管）。
```

- `ai`：AI 主导，正常 agent loop
- `human_pending`：用户已请求人工，等客服接管（客服未到岗前用户消息暂存，AI 可继续兜底）
- `human_takeover`：客服已接管，AI 完全不发回复，所有消息走客服
- `ai_draft`：AI 产出但不发，客服 review（仅 MVP-3）

**状态机出入口补全规则**：

| 转换 | 触发 | 动作 |
|---|---|---|
| `human_takeover` → `ai` | 接管客服连续 **15 分钟无活动**（无消息 / 无心跳） | 后台 cron 自动 `release`，对话追加系统消息"客服暂时无回应，AI 继续为您服务"；触发 Lark @ 该客服 |
| `ai_draft` → `ai` | 客服显式 `release` | 跳过本次 AI 草稿，恢复 AI 直发 |
| `ai_draft` → `human_takeover` | 客服 `reject` 时携带 `rewrite` 字段 | 必须 `rewrite` 非空；不提供改写就只能 `release`，**不允许 reject 后留空 ai_draft** |
| `human_pending` → `ai` | 无客服接管 **10 分钟** 超时 | AI 兜底回复"客服繁忙，已为您创建工单，工程师会回复您" + 调 `create_ticket(category="人工介入")` + Lark 强提醒在线客服；mode 回 `ai` |
| **任意 → `human_takeover`** 的权限规则 | 客服点 `take` | `agent` 只能 take `human_pending` 或自己未接管过的 `ai`；`senior` 可强制 take `agent` 接管的 `human_takeover`（抢单）；`engineer` 可强制 take 任意状态；冲突时按原子 `UPDATE` 决定胜者，败者返回 409 |

### 13.3 客服身份与权限

JWT claims: `{ typ: "staff", sub: <staff_id>, role: "agent" | "senior" | "engineer" }`

| role | 能做什么 | 实际人员（Tevau） |
|---|---|---|
| `agent` | 一线客服。接管会话、回消息、查工单、释放回 AI、转 `engineer` | **2 名 APP 客服**，专门服务 C 端 APP 用户 |
| `senior` | 资深客服。`agent` 全部 + 调 AI 草稿模式 + 让 AI 在工作台代查工具（不发给用户）| 暂无（MVP-3 后视客服规模扩展时启用） |
| `engineer` | 技术客服。`senior` 全部 + 直接查代码 / 查 API 调用日志的完整字段（脱敏放宽给工程师） | **技术对接人**（嘉豪 + 另一对接人），服务 B 端 BU |

**关键产品边界**：
- **C 端 APP 用户**点"转人工" → 走 `agent` role 客服（专属 2 人，独立账号系统）
- **B 端 BU 合作伙伴**点"转人工" → 不走客服，直接转 `engineer` role 技术对接人（事项中心按值班分派给嘉豪 / 另一对接人）
- 事项中心收到 `create_ticket` 后按 **`user_type` + `category` + `role` 三元组** 分派：
  - `user_type=c` → 默认分给 active=true 的 agent 轮值
  - `user_type=b` → 默认分给 active=true 的 engineer 轮值
  - `category=bug` 强制 engineer（无论 user_type）

**关键安全约束**：
- 客服查用户数据时，**和 AI 一样走 query_* 白名单工具，受同样的脱敏规则**（§5.4）
- 客服不能直接执行 SQL / 调任意 API；客服工具调用同样审计
- 客服的会话视图按"已分配给我"过滤，不能看任意会话（否则隐私问题）

| `human_online` | SSE 收到 `mode_change` to `human_takeover` | 对话顶部固定徽章 `[客服 张三 · 已认证]`；输入框 placeholder 改为"向客服 张三 留言..."；AI 不再回复 |
| `human_pending` | SSE 收到 `mode_change` to `human_pending` | 对话内 system 消息"已为您请求人工，请稍候..."；显示客服平均等待时长（如果有） |
| `empty` | 新会话 / 无历史消息 | 中央居中 logo + greeting 文本 + 推荐问题快捷气泡（C/B 端不同） |

### 13.7 阶段实施

| 阶段 | 客服介入实现 |
|---|---|
| **MVP-1** | A 方案：**前端保留"转人工"按钮**（§11 line 551 兜底承诺）——按钮点击后前端**发送一条固定 user message**（如 "我想转人工"）到对话流，AI 通过 prompt 识别意图后自动调 `create_ticket(category="人工介入")` → 推事项中心 + Lark @ 值班客服。**MVP-1 不实现 `/request-human` REST 端点**（§13.5 该端点从 MVP-2 上线）。**网页不显示客服回复**，客服走 Lark 联系用户。**不开发客服工作台**。 |
| **MVP-2** | B 方案：上线 `mode` 字段 + 客服工作台基础版（列表 / 接管 / 释放 / 收发消息 / SSE）+ 客服账号系统。用户体验完整在网页内闭环。 |
| **MVP-3** | C 方案：在 B 上加 AI 辅助（旁观 / 工具代查 / 草稿审核）+ 多客服协作 + KPI 看板。 |

### 13.8 风险与边界

| 风险 | 对策 |
|---|---|
| 客服越权（看到不该看的会话/数据） | 客服查询和 AI 一样走 query_* 白名单 + 脱敏；会话列表按 `assigned_staff_id` 过滤；engineer role 才能放宽脱敏；全量审计 |
| 客服离岗 / 不在线，用户长时间等不到人 | **客服工作时间：北京时间 10:00–19:30**（2 名 APP 客服轮值，具体班表由 HR/客服主管定）。工作时段内：`human_pending` 超过 **10 分钟** 无人接管 → AI 兜底回复"客服繁忙，已为您创建工单，预计 X 时回复" + 触发 Lark @ 在线客服强提醒；非工作时段（19:30–次日 10:00）：用户点转人工时 AI 直接回复"客服当前不在线（工作时间 10:00–19:30），已为您创建工单，明天 10:00 后会有客服跟进" + 建工单进事项中心，待次日处理 |
| AI 已答错但客服没看到，用户已生气 | `human_takeover` 时把最近 5 轮 AI 对话作为"上下文摘要"显示给客服首屏，避免重新摸底 |
| 多客服同时接管同一会话 | `take` 是原子操作（`UPDATE conversations SET assigned_staff_id=? WHERE id=? AND assigned_staff_id IS NULL`），失败返回 409 |
| 客服恶意冒充 / 钓鱼 | 客服消息显示 `[客服 张三 · 已认证]` 徽章；客服账号使用**独立账号系统 + 强密码 + TOTP 2FA**（与 §12.5 ✅3 一致——客服规模 2 人不值得搭 SSO；未来扩展时再升级为 SSO） |
| AI 草稿模式延迟体感差 | 仅高风险 category（如 p0 / 资金类）默认启 ai_draft；其他默认直发；用户能看到"客服正在 review 您的回答…"提示 |

### 13.9 与现有架构的关系

- 与**工单**正交：客服介入是"会话级"，工单是"问题级"。一次客服介入里可能创建/关联多个工单；一个工单可能跨多次客服介入。两套机制并存。
- 与**事项中心**正交：事项中心管工单生命周期（分派/SLA/CTO 升级）；客服介入管对话主导权切换。客服在工作台看到的工单状态来自事项中心 §7.2 回调。
- 与 **AI 工具白名单**复用：客服直接查数据走同一套 query_* 工具，受同样的身份隔离 + 脱敏约束；唯一差异是 `engineer` role 可解锁脱敏（见 §13.3 + §12.5 ✅9）。

### 13.10 与 tawk.to 并存期

**新旧系统并存运行**——APP 版本升级周期长（C 端用户不可能一夜之间全部升级最新 APP），所以 AI 引擎上线后：

- **老 APP 版本用户**：继续走 tawk.to（保留入口不变）
- **新 APP 版本用户**：走本系统（webview 嵌 AI 对话页）
- **客服人员（2 名）需同时巡查两个系统**：tawk.to 后台 + 本系统客服工作台

**对设计的影响**：

| 项 | 应对 |
|---|---|
| 客服工作台 UX | 工作台首页加 tawk.to 旧后台跳转链接，方便快速切换 |
| 数据统计 | MVP-3 可观测面板要把 tawk.to 的客诉量也算进去（人工录入或抓 tawk.to 数据） |
| 退场策略 | 当老 APP 版本用户量 < 5%（或具体阈值待定）时，关闭 tawk.to 入口，触发"系统升级公告" |
| 历史聊天 | 不迁移；老用户在 tawk.to 看历史，新用户在本系统看历史，**两个系统的历史不互通** |

**估算并存期**：6-12 个月（取决于 APP 版本升级率，需要 PM/产品观察后决定退场时点）。

## 附录 A：术语表

- **AI 引擎**：本文档定义的对话式 AI 服务。不含分派/SLA 升级。
- **事项中心**：公司另一系统（待造），负责工单的分派、SLA 计时、升级到 CTO。AI 引擎通过 webhook 向其推送工单、接收状态回调。
- **CQ**：Consulting Question，咨询类问题，可由 AI 直接答。
- **BU**：Business Unit，B 端合作伙伴账户（如 `BU00243780`）。
- **客服工作台（Staff Console）**：客服人员使用的独立网页应用，用于接管对话、回消息、查看用户上下文、调 AI 工具代查数据。详见 §13.6。
- **接管 / 释放**：客服工作台两个核心动作。"接管"把会话从 AI 主导切到客服主导（mode=human_takeover）；"释放"把控制权交还 AI。
- **AI 草稿模式（ai_draft）**：会话状态之一，AI 产出回复但不直接发给用户，由客服 review 后才发。仅 MVP-3。
