# 客服在线开关 + 派单（替代排班）— Design

**日期**：2026-06-04
**作者**：caril（产品决策） + Claude（设计落地）
**状态**：待 review

## 1. 背景与目标

### 1.1 现状

- 客服值班依赖 `staff_shifts` 排班表，要 admin 后台手工建条目（一行一段班次）。
- 转人工是**抢单池**模型：会话进 `mode=human_pending`，所有客服都能看见，谁先点 `/take` 谁抢到（原子 update `WHERE assigned_staff_id IS NULL`）。
- AI 在班外（任何 staff 都不在 shifts 时段内）会告诉用户"客服班外，下次上班是 X 时"。
- 实际业务侧没人维护排班，shifts 表里现在是 0 条数据；班外措辞从未真正生效。

### 1.2 目标

替换为更简单的"在线开关 + 服务端派单"模型：

1. 客服登录后默认 offline，工作台顶栏一个开关，点击切到 online 才接单。
2. 转人工时服务端按"最少在聊"算法主动派给一位 online 客服（不是所有人都看到）。
3. 派给某人后 60 秒内没接管 → 自动回退到开放池，所有 online 客服可抢（兜底防漏）。
4. 关闭开关：未接管的派单自动释放回池子；已接管的会话允许聊完。
5. 删除 shifts 全套（表 + 后端 API + admin 排班页）。
6. 班外（全员 offline）AI 措辞简化为"客服当前不在线，已为您留单，上线后会主动联系您"，不再有具体时间。
7. 新增 RBAC 权限项 `chat.dispatch` 控制"哪些角色进派单池"，admin 在权限矩阵自配，默认 `agent / senior / supervisor=true`。

### 1.3 非目标

- 不实现派单超时后自动再派给另一个人——超时即回开放池，简化兜底。
- 不实现"全局营业时间"配置——纯按 online 数量判断班外。
- 不强制关开关时释放正在聊的（`human_takeover`）会话——客服自己点"已解决"。
- 不动 C 端用户侧的转人工入口和 UX，本次仅改服务端语义和客服侧 UI。

## 2. 架构总览

```
[C端 用户转人工 或 AI create_ticket(人工介入)]
       │
       ▼
  mode = human_pending
       │
       ▼
  dispatch_to_human_pending(conv_id)
       │
  ┌────┴────┐
有 online +  无 online +
有 chat.dispatch 权限的客服  有权限的客服
       │              │
       ▼              ▼
  最少在聊       assigned_staff_id = NULL
  算法选一人       no_one_online = True
       │              │
       ▼              ▼
  assigned_      AI 措辞："客服
  staff_id =      当前不在线..."
  picked +
  assigned_at = now
       │
       ▼
  SSE 推 conversation_assigned 给该客服
  (该客服工作台高亮/响铃)
       │
       ▼
  60s 内 take?
       │
   ┌───┴───┐
  是       否
   │       │
   ▼       ▼
human_   超时 watcher 清空 assigned_staff_id
takeover  → SSE conversation_assignment_cleared
(正式接管) → 所有 online 客服侧的"未接管池"出现这条
           → 谁先 take 谁抢（抢单兜底）
```

**核心模块**：

- `staff_presence`（**复用**）：承载在线开关。`status ∈ {online, offline}`（去掉 `away`），心跳 5 分钟。
- `services/dispatch.py`（**新增**）：
  - `dispatch_to_human_pending(conv_id) → {dispatched: bool, staff_id: str | None, no_one_online: bool}`
  - 后台 watcher：每 10 秒扫一遍超时的派单回退到池子。
- `rbac.PERMISSION_KEYS`（**改**）：加 `chat.dispatch`。

## 3. 数据模型

### 3.1 schema 改动

| 表 | 改动 |
|---|---|
| `staff_shifts` | **DROP TABLE**（一次性删，无 deprecation 窗口） |
| `staff_presence` | 不动表结构。`status` 值收敛为 `online` / `offline`；既有 `away` 行迁移为 `offline` |
| `conversations` | 不动表结构。`assigned_staff_id` / `assigned_at` 既有字段，新语义：`mode='human_pending' AND assigned_staff_id IS NOT NULL` = "已派给某人未接管"；`mode='human_pending' AND assigned_staff_id IS NULL` = "在开放池等抢" |
| `role_permissions` | 不动表结构。运行时 `PERMISSION_KEYS` 加 `chat.dispatch`。默认值：`agent / senior / supervisor = true`，其他 false |

### 3.2 状态机（会话 mode）

```
ai ──→ human_pending（assigned_staff_id=NULL，开放池）
       │
   dispatch 派给某人
       │
       ▼
       human_pending（assigned_staff_id=X，X 60s 内可 take）
       │
   ┌───┴──────────────┐
take                  60s 超时
   │                  │
   ▼                  ▼
human_takeover     human_pending（assigned_staff_id=NULL，回开放池）
   │                  │
release / resolve     take（任何 online 客服）
   │                  │
   ▼                  ▼
   ai            human_takeover
```

## 4. API 改动

### 4.1 客服端

| 端点 | 改动 | 说明 |
|---|---|---|
| `POST /staff/api/v1/presence` | **改语义** | 现有：心跳 upsert。新副作用：当 `body.status='offline'` 时同步释放 `WHERE assigned_staff_id=:me AND mode='human_pending'` 的会话回开放池，并对每个释放的 conv_id 推 SSE `conversation_assignment_cleared` |
| `POST /staff/api/v1/conversations/{id}/take` | **微调 WHERE** | `WHERE id=:id AND (assigned_staff_id IS NULL OR assigned_staff_id=:me)` —— 允许被派的人接，也允许超时回退后任何 online 客服抢 |
| `GET /staff/api/v1/conversations?status=human_pending` | **微调过滤** | 加 `AND (assigned_staff_id IS NULL OR assigned_staff_id=:me)`：派给别人未超时的不在我这条列表里 |

| 端点 | 改动 |
|---|---|
| `GET/POST/PATCH/DELETE /admin/api/v1/shifts*` | **全删** |
| `GET /admin/api/v1/presence` | 保留，作为后台监控"谁在线" |
| 权限矩阵 (`/admin/api/v1/rbac/*`) | **自动多一列** `chat.dispatch`（matrix 接口动态读 `PERMISSION_KEYS`，UI 不用改） |

| 事件 type | 推送对象 | 说明 |
|---|---|---|
| `conversation_assigned` | 被派的那位客服 | 工作台高亮 / 置顶 / 响铃 |
| `conversation_assignment_cleared` | 所有 online 客服 | 开放池新增一条，"未接管" tab 自动出现 |

## 5. 派单算法（dispatch service）

### 5.1 派单 SQL

```sql
SELECT p.staff_id,
       (SELECT COUNT(*) FROM conversations c
        WHERE c.mode='human_takeover' AND c.assigned_staff_id=p.staff_id) AS load
  FROM staff_presence p
  JOIN staff s ON s.id = p.staff_id
 WHERE p.status='online'
   AND p.last_seen_at >= :cutoff            -- 心跳窗口（5min，防僵尸 online）
   AND s.role = ANY(:roles_with_chat_dispatch)  -- RBAC: chat.dispatch=true 的角色
 ORDER BY load ASC, p.last_seen_at ASC       -- tiebreaker: 最近活跃优先
 LIMIT 1
```

`:cutoff` = `now() - INTERVAL '5 minutes'`（SQLite 测试库等价用 strftime）
`:roles_with_chat_dispatch` 从 rbac 缓存里 build：遍历 6 个角色查 `is_permitted(role, 'chat.dispatch')` 为 True 的列表

> 注意 SQLite 测试库写法与 Postgres 不同（CAST(:p AS TEXT) 等），见 [project_sqlite-vs-postgres-test-gap](memory)。本 spec 实施时所有派单 SQL 必须在 PG 验真。
> 实现要点：`s.role = ANY(:roles)` 是 PG 写法；为兼容 SQLite 测试，用 `databases` 库的列表展开成 `s.role IN (:r0, :r1, ...)`，由代码动态拼。

### 5.2 派单流程

```python
async def dispatch_to_human_pending(conv_id: int) -> dict:
    roles = await _roles_with_chat_dispatch()  # rbac 查
    picked = await _pick_least_loaded(roles)   # 上面那条 SQL
    if not picked:
        return {"dispatched": False, "no_one_online": True}

    rowcount = await db.execute(
        "UPDATE conversations SET assigned_staff_id=:sid, assigned_at=:now "
        "WHERE id=:id AND mode='human_pending' AND assigned_staff_id IS NULL",
        {"sid": picked, "now": now_str(), "id": conv_id},
    )
    if rowcount == 0:
        # 并发：另一个 dispatch 调用已经派过 / 客服已 take。视为成功，不重派。
        return {"dispatched": False, "already_assigned": True}

    publish_conversation_event(conv_id, {
        "type": "conversation_assigned",
        "staff_id": picked,
    })
    return {"dispatched": True, "staff_id": picked, "no_one_online": False}
```

### 5.3 调用方接入点

转人工有**两个入口**，都改用 dispatch：

1. `api/user_events.py::request_human` (`POST /api/v1/conversations/{id}/request-human`) —— C 端用户主动按转人工触发。
   - 改动：删 `shifts_query.any_on_shift` / `next_shift_start` 调用 + `off_hours_payload` 构造；在 `set_mode(conv_id, 'human_pending')` 之后追加 `result = await dispatch_to_human_pending(conv_id)`；响应里把 `off_hours` / `next_shift_start` 换成 `no_one_online`（取自 result）。
2. `agent/tools/create_ticket.py::_ensure_human_pending` —— AI 工具 `create_ticket(category='人工介入')` 触发。
   - 改动：把整段 `shifts_query.*` 替换成 `await dispatch_to_human_pending(conv_id)`；返回值映射 `{no_one_online: bool}`（旧的 `off_hours` / `next_shift_start` 字段删掉）。AI prompt 据 `no_one_online` 选措辞。

### 5.4 超时回退（background watcher）

`services/dispatch.py` 提供 `start_watcher(app)`，在 `lifespan` 里 spawn：

```python
async def _watcher_loop():
    while True:
        try:
            rows = await db.fetch_all(
                "UPDATE conversations "
                "SET assigned_staff_id=NULL, assigned_at=NULL "
                "WHERE mode='human_pending' "
                "  AND assigned_staff_id IS NOT NULL "
                "  AND assigned_at < :cutoff "
                "RETURNING id",
                {"cutoff": _utc_minus_seconds(60)},
            )
            for r in rows:
                publish_conversation_event(int(r["id"]), {
                    "type": "conversation_assignment_cleared",
                })
        except Exception:
            logger.exception("dispatch watcher iteration failed")
        await asyncio.sleep(10)
```

**注意**：SQLite 不支持 `UPDATE ... RETURNING`（3.35+ 才支持，aiosqlite 视版本而定）。如果测试 stack 跑不通，改写成"先 SELECT id → UPDATE → 用收集到的 id 推 SSE"两步走。生产 PG 用 RETURNING 单步。

## 6. 关开关副作用

### 6.1 POST /staff/api/v1/presence body={status:"offline"} 的完整流程

分层职责：

- `persistence/staff_presence.py::heartbeat(staff_id, status)` —— 仍只负责 upsert，签名/返回值不变（`-> None`）
- `persistence/staff_presence.py::release_pending_assignments(staff_id) -> list[int]` —— **新增**，做释放并 RETURNING 一组 conv_id
- `api/staff_presence.py::heartbeat`（FastAPI 端点）—— 串起两步 + 推 SSE

端点实现：

```python
@router.post("/staff/api/v1/presence")
async def heartbeat(body: HeartbeatIn, staff: dict = Depends(require_staff)):
    status = body.status if body.status in _VALID_STATUS else "online"
    sid = str(staff.get("sub", ""))
    if not sid:
        return {"ok": False}
    await staff_presence.heartbeat(sid, status)
    released_count = 0
    if status == "offline":
        released_ids = await staff_presence.release_pending_assignments(sid)
        for cid in released_ids:
            publish_conversation_event(cid, {
                "type": "conversation_assignment_cleared",
            })
        released_count = len(released_ids)
    return {"ok": True, "released_count": released_count}
```

`release_pending_assignments` SQL：

```sql
UPDATE conversations
   SET assigned_staff_id = NULL, assigned_at = NULL
 WHERE assigned_staff_id = :sid
   AND mode = 'human_pending'
RETURNING id
```

- `_VALID_STATUS` 收敛为 `{"online", "offline"}`（删 `away`）
- `human_takeover` 的会话**不动**——继续聊，自己点"已解决"才放手
- 返回值新加 `released_count`，前端按 >0 时弹 message.info

### 6.2 前端开关 UX

- 工作台顶栏：toggle（`在线` / `离线`），登录默认 `离线`
- `online → offline`：调 `POST /presence body={status:"offline"}`，根据返回 `released_count` 弹 `message.info("已释放 N 个未接管会话给其他客服")`（N=0 时不弹）
- `offline → online`：调 `POST /presence body={status:"online"}`，启动心跳定时器（5 分钟一次）
- `offline` 状态下：工作台底部固定一条提示"你当前离线，不会接到新会话"，进行中的会话照常显示

| 用例 | 类型 |
|---|---|

## 12. 风险与回退

- **风险 1**：dispatch watcher 跑挂导致超时派单永远卡在某人头上。**缓解**：异常吃掉继续循环 + 加 `dispatch_watcher_iterations_total` metric，掉 0 告警。
- **风险 2**：客服关浏览器没关开关 → 心跳停 5 分钟内仍可能被派单，用户等 60 秒才回池。**缓解**：心跳窗口 5min 是已有值；可接受的最坏延迟是 5min + 60s。
- **风险 3**：删除 shifts 后，老 i18n key 在线上有缓存调用。**缓解**：i18n 改动随后端代码一并部署，无独立缓存层。
- **回退**：watcher 出严重 bug 时，临时把 `WHERE assigned_at < now()-60s` 改成 `WHERE 1=0` 关闭，回退到"被派的人不接就永久卡住"——比派错好。但已删的 shifts 代码无法回退，需要重写。
